# DeerFlow 产品化改造 PRD

## 1. 背景

当前项目基于开源 DeerFlow。目标不是简单换一套页面或改几个品牌名，而是把它改造成一个可长期自主管理、可部署、可运营、可持续跟随上游升级的自有产品。

DeerFlow 本身已经具备完整的 AI Agent 能力，包括前端聊天界面、FastAPI Gateway、LangGraph 运行时、MCP/Skills/Extensions、持久化、调度任务、外部 IM 接入等能力。产品化改造应尽量复用这些核心能力，把自有业务沉淀在独立层，减少直接改动上游核心代码。

## 2. 产品目标

1. 建立自有品牌与自有页面体系，去除默认 DeerFlow 产品表达。
2. 建立自有数据管理体系，包括用户、组织、业务数据、审计、文件、Agent 运行数据和配置数据。
3. 支持私有化部署与后续 SaaS 化演进。
4. 保持与上游 DeerFlow 的升级兼容，未来可定期合并上游版本。
5. 将二次开发限制在清晰边界内，避免后续升级时出现大量冲突。

## 3. 非目标

1. 不建议全量重写 DeerFlow 后端 Agent Runtime。
2. 不建议把所有 `deerflow` 包名、内部模块名一次性改成自有名称。
3. 不建议直接在核心运行时里混入业务逻辑。
4. 第一阶段不追求完整多租户 SaaS 计费体系，先把组织、权限、数据隔离边界打牢。

## 4. 用户与场景

目标用户包括：

1. 内部运营或业务团队：使用自有工作台管理任务、知识、文件和 Agent 执行结果。
2. 企业客户管理员：管理组织、成员、权限、审计和集成配置。
3. 普通终端用户：通过 Web 或外部 IM 使用智能助手能力。
4. 系统运维人员：负责部署、升级、备份、监控和故障恢复。

核心场景包括：

1. 用户登录自有品牌系统，进入工作台。
2. 用户创建线程、上传文件、调用 Agent 完成任务。
3. 管理员管理组织、成员、角色、知识库和集成。
4. 系统记录完整操作审计和 Agent 运行审计。
5. 运维人员可按版本升级 DeerFlow 上游，并完成回归验证。

## 5. 总体方案

采用“上游内核 + 自有产品层 + 扩展插件层”的结构。

| 层级 | 内容 | 改造原则 |
| --- | --- | --- |
| 上游内核 | DeerFlow Harness、Gateway、Agent Runtime、MCP、Skills、Scheduler | 尽量少改，必要修改记录补丁原因 |
| 自有产品层 | 品牌、导航、页面、业务模块、运营后台 | 放在独立目录，通过配置和适配器接入 |
| 扩展插件层 | 自有 API、权限、中间件、审计、额度、业务工具 | 优先使用 DeerFlow Extensions 机制 |
| 数据层 | PostgreSQL、对象存储、运行时文件、业务数据库 | DeerFlow 数据与业务数据逻辑隔离 |

核心原则：不要把 DeerFlow 改成“看不出 DeerFlow 的内部结构”，而是把它作为底座，在外层建立自己的产品。

## 6. 前端改造需求

### 6.1 品牌配置

新增统一品牌配置层，集中管理：

1. 产品名称。
2. Logo、favicon、主题色。
3. 页面标题与 metadata。
4. 外链地址，如官网、帮助文档、隐私协议、用户协议。
5. 默认首页和登录后入口。

建议目录：

```text
frontend/src/product/
├── brand.ts
├── features.ts
├── navigation.ts
├── routes.ts
└── api/
```

### 6.2 页面体系

自有页面应尽量放在独立路由分组中，例如：

```text
frontend/src/app/(product)/
├── dashboard/
├── workspace/
├── knowledge/
├── files/
├── integrations/
├── admin/
└── settings/
```

需要保留并封装 DeerFlow 原有聊天、线程、工具调用展示能力。不要直接删除原有核心页面，先通过导航和路由策略隐藏或替换默认入口。

### 6.3 功能开关

新增功能开关配置，用于控制：

1. 是否显示 GitHub Star、上游文档、开源社区链接。
2. 是否启用外部 IM 集成入口。
3. 是否启用 Skills、MCP、Scheduled Tasks 等高级入口。
4. 是否启用管理员后台。
5. 是否启用多租户相关页面。

### 6.4 前端验收标准

1. 页面中默认 DeerFlow 品牌露出被自有品牌替换。
2. 用户登录后进入自有工作台。
3. 原有 Agent 聊天能力可正常使用。
4. 导航、设置、帮助、空状态、错误页均使用自有文案。
5. 前端 `pnpm check` 通过。

## 7. 后端改造需求

### 7.1 扩展优先

后端自有业务能力优先通过 DeerFlow Extensions 实现。根据当前仓库结构，DeerFlow 支持扩展贡献：

1. Middleware。
2. Task lifecycle。
3. System model observers。
4. Gateway services。
5. FastAPI HTTP routers。

建议新增自有扩展包：

```text
backend/extensions/sources/your_product_extension/
```

或以独立包形式维护，再通过 `config.yaml -> plugins` 启用。

### 7.2 自有 API

新增自有 API，建议统一挂载在：

```text
/api/product/*
```

首批 API 包括：

1. 当前用户与组织上下文。
2. 组织、成员、角色管理。
3. 自有知识库管理。
4. 文件与资源管理。
5. 审计日志查询。
6. 业务配置读取。
7. 额度与使用量统计。

### 7.3 权限与租户

需要建立组织维度的数据边界：

1. 用户必须属于一个或多个组织。
2. 每个线程、文件、知识库、集成配置、审计日志都应归属组织或用户。
3. 后端必须做资源归属校验，不能只依赖前端隐藏。
4. 管理员 API 需要 RBAC 权限控制。
5. 外部集成凭证必须按用户或组织隔离。

需要重点审计的对象：

1. Threads。
2. Runs。
3. Files。
4. Memories。
5. Skills。
6. MCP Servers。
7. OAuth Credentials。
8. Scheduled Tasks。
9. Managed Subagents。
10. Artifacts。

当前 DeerFlow 部分能力可能是部署级或用户级设计，SaaS 化前必须逐项确认是否需要加组织边界。

### 7.4 后端验收标准

1. 自有扩展可随 Gateway 启动加载。
2. 自有 API 可返回登录用户、组织、权限和业务配置。
3. 关键资源访问具备后端权限校验。
4. Agent 原有运行链路不被破坏。
5. Backend 默认测试与关键 API 测试通过。

## 8. 数据方案

### 8.1 数据库

生产环境使用 PostgreSQL。SQLite 只作为本地开发或轻量测试使用。

建议逻辑隔离：

1. DeerFlow 原生表：保留原项目迁移和结构。
2. 自有业务表：放在独立 schema 或明确前缀中。
3. 审计表：独立建模，便于长期归档和查询。

示例配置方向：

```yaml
database:
  backend: postgres
  postgres_url: ${DATABASE_URL}
  postgres_schema: deerflow

agent_storage:
  backend: db
```

自有业务数据可以使用独立 schema，例如 `product`，由自有扩展的 repository 层管理。

### 8.2 文件与运行时数据

必须持久化：

1. `DEER_FLOW_HOME`。
2. 用户上传文件。
3. Agent 运行产物。
4. 扩展配置。
5. 日志与审计数据。

生产建议：

1. 小规模私有化：本地挂载卷 + 定期备份。
2. 多实例或 SaaS：对象存储 + PostgreSQL + Redis/队列。
3. 敏感文件：加密存储，下载前做权限校验。

### 8.3 备份策略

1. PostgreSQL 每日全量备份，关键业务增量备份。
2. 对象存储开启版本管理。
3. 每次升级前执行数据库快照。
4. 保留可回滚镜像版本。

## 9. 配置与部署

### 9.1 配置原则

1. `config.yaml` 作为运维级配置，不建议运行时频繁改写。
2. `extensions_config.json` 可用于 MCP、Skills 等运行时配置。
3. 密钥必须通过环境变量或密钥管理系统注入。
4. 不提交真实 `config.yaml`、`extensions_config.json` 和任何密钥。

### 9.2 部署拓扑

第一阶段可使用 Docker Compose：

```text
Nginx -> Frontend -> Gateway -> PostgreSQL
                         ├── DEER_FLOW_HOME volume
                         ├── Object Storage
                         └── Sandbox / Provisioner
```

后续如需多实例部署，再引入：

1. Kubernetes。
2. 独立 Scheduler。
3. Redis 或队列。
4. 统一日志与指标系统。
5. 分布式锁或任务归属机制。

## 10. 上游兼容与升级策略

### 10.1 Git 策略

建议将当前开源仓库作为 upstream，自有仓库作为 origin：

```bash
git remote rename origin upstream
git remote add origin <your-private-repo-url>
git fetch upstream
```

推荐分支：

1. `main`：自有产品稳定分支。
2. `develop`：日常开发分支。
3. `upgrade/deerflow-<version>`：上游升级验证分支。
4. `codex/*` 或 `feature/*`：单功能开发分支。

### 10.2 补丁台账

新增文档记录所有对上游核心的直接修改：

```text
docs/upstream-patches.md
```

每条记录包括：

1. 修改文件。
2. 修改原因。
3. 是否可迁移到 extension。
4. 上游升级冲突风险。
5. 回归测试方式。

### 10.3 升级流程

1. 选择上游 release 或固定 commit，不直接跟随上游 `main`。
2. 创建 `upgrade/deerflow-<version>` 分支。
3. 合并或 rebase 上游版本。
4. 解决冲突。
5. 执行数据库迁移演练。
6. 执行后端测试、前端检查和端到端冒烟测试。
7. 在 staging 环境验证。
8. 灰度发布。
9. 保留回滚镜像、数据库快照和对象存储快照。

### 10.4 升级验收标准

1. 上游合并冲突数量可控，并有记录。
2. 自有扩展不需要大规模重写。
3. 数据库迁移可重复执行。
4. 老数据可正常读取。
5. 核心 Agent 流程、登录、权限、文件、知识库、调度任务通过回归。

## 11. 法务与开源合规

DeerFlow 当前为 MIT License。产品化时需要：

1. 保留原始 License 和版权声明。
2. 不移除上游必要的开源声明。
3. 自有品牌不得暗示与原项目官方存在授权或隶属关系。
4. 自有代码可闭源，但需要维护清晰的第三方依赖清单。
5. 对外分发镜像或安装包时附带开源许可信息。

## 12. 实施计划

### 阶段一：基础接管

周期：1-2 周。

交付物：

1. 私有 Git 仓库与 upstream 远程配置。
2. 当前上游版本基线 tag。
3. PostgreSQL 开发环境。
4. 生产配置模板。
5. 自有品牌配置层。
6. 上游补丁台账。

### 阶段二：品牌与页面

周期：2-3 周。

交付物：

1. 自有首页或工作台。
2. 自有导航体系。
3. 登录后默认入口。
4. 品牌、文案、外链替换。
5. 功能开关。
6. 原有聊天能力封装接入。

### 阶段三：数据与权限

周期：3-5 周。

交付物：

1. 组织、成员、角色模型。
2. 自有业务 schema。
3. 资源归属校验。
4. 审计日志。
5. 文件与知识库管理。
6. 管理后台基础能力。

### 阶段四：扩展与运营

周期：3-6 周。

交付物：

1. 自有 DeerFlow Extension。
2. 业务 API。
3. 额度统计。
4. 运维监控。
5. 备份恢复流程。
6. 升级演练流程。

### 阶段五：SaaS 化增强

周期：视业务规模决定。

交付物：

1. 多租户隔离增强。
2. 计费与套餐。
3. 多实例部署。
4. 灰度发布。
5. 企业 SSO。
6. 更完整的安全审计。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 直接改动上游核心过多 | 后续升级困难 | 扩展优先，核心补丁必须登记 |
| 数据边界不清 | SaaS 化风险高 | 早期建立组织与资源归属模型 |
| 配置与密钥混乱 | 安全事故 | 使用环境变量和密钥管理，禁止提交真实配置 |
| 多实例部署过早 | 增加复杂度 | 第一阶段先单实例稳定，后续再演进 |
| 上游升级破坏自有功能 | 回归成本高 | 建立升级分支、测试集和升级演练 |
| 前端硬编码品牌 | 替换成本高 | 建立统一品牌配置和功能开关 |

## 14. 验收清单

第一版产品化改造完成时，应满足：

1. 可使用自有域名、自有品牌访问系统。
2. 用户登录、创建线程、执行 Agent 任务、查看结果流程正常。
3. 自有业务页面与 DeerFlow 原有能力完成整合。
4. 生产环境使用 PostgreSQL 持久化。
5. `DEER_FLOW_HOME` 等运行时数据可持久化和备份。
6. 关键数据有组织或用户归属。
7. 管理员可查看基础审计日志。
8. 项目保留 upstream，可执行上游升级演练。
9. 所有直接修改上游核心的补丁有台账。
10. 前端检查、后端测试、端到端冒烟测试通过。

## 15. 近期建议任务

建议下一步先完成以下事项：

1. 创建私有仓库，并将当前开源远程改为 `upstream`。
2. 新增 `frontend/src/product` 品牌配置层。
3. 新增自有 Extension 骨架，并挂载 `/api/product/health`。
4. 切换本地和测试环境到 PostgreSQL。
5. 建立 `docs/upstream-patches.md`。
6. 写第一组冒烟测试：登录、打开工作台、创建线程、执行一次 Agent、查看历史记录。
