本机首次运行请先按[中文快速启动指南](../快速启动.md)准备依赖、模型配置并启动服务；本 PRD 聚焦试运行环境的上线验收与运维闭环。

## 1. 背景与目标

当前工程已具备自有品牌首页与工作台基础，并保留 DeerFlow 的会话、Agent、认证与文件流程。此 MVP 的目标是把可演示的产品外壳推进到**能够在自有环境里安全、可恢复地试运行**：明确数据落点，部署后能登录和完成一次 Agent 任务，用户能找到自己的历史及文件，运维能备份并恢复，且下次升级可知道自定义改动在哪里。

本 PRD 限定首期上线闭环。账号组织模型、数据治理和上游兼容的长期能力仍以[整体 PRD](产品化需求与实施记录.md)为准；未达成本 PRD 的上线门槛前，不宣传为可对外销售的多租户 SaaS。

## 2. 首期用户与场景

首期假设单一组织、自主托管，组织内有普通使用者和部署管理员。管理员可以是同一位工程师，但产品权限仍分开处理。

主场景：管理员部署实例并设置模型/搜索密钥；用户进入品牌化工作台，登录后创建会话、上传文件、发起 Agent 任务、查看流式进度与产物，稍后能从历史中恢复会话；管理员验证数据库和文件备份，并依据版本清单升级或回退应用。

## 3. 首期范围

### P0：上线必需

1. 品牌自有：页面标题、图标、首页、登录后工作台、导航、帮助入口和中英文文案一致；保留开源许可及第三方声明。
2. 登录与权限：明确账号如何创建、是否允许注册；未登录页面和 API 行为一致；所有资源访问由服务端验证 owner/管理员权限。
3. Agent 主路径：登录、创建会话、发消息、SSE 更新、工具/子任务状态、取消、断线恢复、历史读取和错误提示可用。
4. 文件闭环：上传、产物查看/下载与所有权检查可用；明确上传上限、保留期及文件实际存储位置。
5. 生产存储：目标环境使用受支持数据库（推荐 PostgreSQL）；数据库、工作区文件、记忆、配置和密钥进入资产清单，容器重建不丢失持久数据。
6. 备份与恢复：同时备份数据库和文件卷；记录加密、保留周期和恢复步骤；上线前在隔离环境成功恢复一次。
7. 可发布制品：前后端版本一致，环境变量/密钥说明清楚；健康检查、日志、备份状态和升级步骤可供运维排障。
8. 上游基线：确认本分支对应的 DeerFlow commit/tag；自有补丁写入台账；候选版本至少完成构建、测试、产品主路径和迁移副本演练。

### P1：试运行后增强

- 产品管理页编辑业务设置并查看审计事件。
- 自助数据导出、账户删除编排和可追踪进度。
- 全局文件索引、筛选、回收站策略及批量管理。
- 按用户/部门管理配额、运行报表与组织级共享资源。

完整账号导出和账户擦除尚未实现。账号页当前的浏览器 JSON 导出尽力汇总 Gateway 可读资源；后台任务可按单一范围导出偏好、会话可见历史、项目元数据、计划任务定义、自建 Agent、当前记忆后端返回的 owner view 和 Gateway 当前可读取的受限文件，也可将这七类范围合并为带 `manifest.json` 的 `account` ZIP。组合包始终标记为 `partial`；子包保留各自完整度说明。记忆覆盖范围随配置后端而异，文件仅含线程平铺上传/输出、符合限制的会话工作区文件和项目资料架 active 原件。删除任务现支持本人偏好、计划任务定义、自建 Agent、会话历史、项目空间和当前记忆后端可清除的记忆；任务定义删除保留运行历史及生成的会话内容，执行中的 occurrence 不会删除；项目空间删除会把活动资料移入回收站，会话正文保留；跨存储清理不保证原子回滚。文件中心的逐项删除与回收站操作也不能代替账号级文件清理。这些能力都不能替代完整导出/擦除闭环。若法律、合同或试点政策要求上线即具备，应将其提升为发布阻断项并单独实现验收；不能把单资源删除当成完整删除闭环。

## 4. 用户流程和验收

| ID                   | 验收条件                                                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| LA-01 品牌入口       | 首页、登录、工作台、浏览器标题和图标呈现产品身份；移动/窄窗口下导航和内容仍可操作。                                                       |
| LA-02 身份边界       | 未登录访问受保护页面会进入登录流程；用户 A 不能读取或下载用户 B 的会话、产物和上传文件。修改 URL、thread/file ID 或请求体均不能绕过检查。 |
| LA-03 Agent 主流程   | 用户可以新建会话、提交任务、观察增量事件和产物；刷新后历史可继续读取；取消后运行终止并展示终态；网络中断后恢复不重复显示消息。            |
| LA-04 部署持久性     | 重启前后的账号、会话、配置及文件一致；应用镜像可替换而不覆盖持久卷。                                                                      |
| LA-05 备份恢复       | 使用独立测试环境、生产格式备份恢复；登录并打开一条会话和一个文件；记录耗时、数据时间点和缺陷。                                            |
| LA-06 运行维护       | Gateway、前端、Nginx 健康检查正常；应用错误能按 request/run/thread ID 关联日志；日志不包含密钥和不必要的完整提示词/正文。                 |
| LA-07 发布回退       | 机器可校验的发布清单记录产品版本/commit、DeerFlow 官方 tag/commit、镜像 digest、配置与迁移版本、备份标识及升级兼容/隔离恢复证据；验证上一应用版本如何回退。若迁移不可逆，发布说明须给出恢复路径。 |
| LA-08 双语与可访问性 | 中英文可切换或按现有 locale 正常显示；键盘可完成登录、发起任务、切换导航等主要操作；错误与空状态可理解。                                  |

验收数据用合成测试账号和虚构内容，不使用真实客户资料。测试报告注明 commit、运行环境、测试账号权限、结果和已知问题。

## 5. 配置与运行要求

- 开发人员：Node.js 22+、pnpm 10.26.2+、Python/uv 版本依仓库配置，复制 example 配置后使用 `make dev`。
- 试运行环境：部署到明确的内网/受控环境，入口经 TLS 终止代理暴露；不直接对公网暴露 Gateway 内部端口。
- 生产存储：PostgreSQL；数据库连接凭据由 secret 注入。文件和用户工作区使用持久卷；备份介质与运行主机分离。
- 第三方服务：模型、搜索、对象存储、OIDC 等逐项列出数据发送范围、地区和凭证责任人；未配置的集成默认关闭。
- 版本记录：每次发布保存产品版本、上游 commit、配置模板版本、迁移版本、镜像 digest、回归结果和备份标识。
- 不以浏览器 feature flag 隐藏页面作为权限控制；服务端必须阻断未授权的读写。

仓库开发启动顺序：根目录先 `make config`，再 `make install`，最后 `make dev`。首次部署应使用环境专属配置和密钥，不能复制开发者本机的 `config.yaml` 或 SQLite 数据直接作为生产环境。

## 6. 里程碑与发布闸门

### M0：基线与资产盘点

确认 upstream Git 来源和真实 commit；列出用户、checkpoint、run events、Agent 设置、记忆、上传文件与沙箱内容的存储位置；确认认证策略、数据保留和外部服务名单。输出架构图、基线记录和数据资产表。

### M1：产品闭环与接口

检查自有首页/导航/登录/工作台；产品 bootstrap、用户偏好、首版审计和在线品牌配置已有自有 API、独立迁移及前端接入。产品后台数据任务支持偏好与计划任务定义导出/删除，以及会话历史、项目元数据、自建 Agent、记忆 owner view 和受限文件的单范围部分导出；API 由 operator 配置控制，worker 使用 owner 检查、持久租约、一人一个活动任务和每小时十次限额。个人数据页提供任务状态、取消和短期下载；两种删除均要求精确短语二次确认，计划任务删除会保留运行历史及会话产物，六类非偏好导出均标记为 `partial` 并说明覆盖范围。账号页还提供尽力读取当前用户可见资源的浏览器 JSON 导出。仍需交付完整账号后台导出/擦除、跨存储文件索引和 PostgreSQL 迁移演练；保留现有登录和聊天内核。

### M2：生产部署与数据安全

用 PostgreSQL 与持久文件卷部署；完成已有数据迁移或明确新实例策略；接入日志和健康检查；完成备份恢复演练及访问隔离测试。

### M3：试点和版本治理

邀请内部试点用户完成任务，修复阻塞问题；固定首个产品 release；执行候选上游升级演练，将冲突及必要操作记入补丁台账；形成运维手册与回退说明。

**允许试点的闸门：** LA-01 至 LA-07 全部通过；LA-08 的阻塞缺陷清零；上游来源及主要补丁已记录；无开放的 P0 安全问题。若数据导出/账户删除被业务或合规列为必须能力，未验收前不开放真实用户数据。

## 7. 指标与观测

试点阶段关注：任务成功率、Agent 运行失败原因、首次响应时间、SSE 中断恢复成功率、上传/产物访问失败率、备份成功率和恢复耗时、越权用例通过率、未归属上游补丁数量。运行/token/成本统计为估算指标，未建立对账前不能当作计费数据。

每个指标指定来源、聚合窗口、隐私保留期和责任人。日志优先保存结构化事件、request/run/thread ID 和错误分类，避免默认持久化完整用户对话。

## 8. 风险和待补业务参数

- **Git 基线不明：** 当前项目化副本需先恢复真实上游基线，否则升级兼容只能靠人工 diff，无法证明可重复合并。
- **数据分散：** 数据库备份不覆盖工作区、文件、记忆和运行配置；必须按资产清单演练恢复。
- **单用户模型不等于组织 SaaS：** 首期限制为单组织实例，不能宣称共享实例租户隔离已完成。
- **数据库样例不等于生产迁移：** PostgreSQL 配置和 Compose 覆盖必须通过真实数据迁移与性能/恢复演练。
- **自动清除范围不完整：** 单个资源删除不自动意味着 checkpoint、日志、备份中的相关数据已被擦除。

排期前由产品/运维补齐：试点人数和并发、注册方式、登录方式、部署位置、模型供应商与数据区域、数据保留/删除要求、RPO/RTO、旧数据是否迁入以及试点支持时间。
