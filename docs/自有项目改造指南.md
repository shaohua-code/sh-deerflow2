# DeerFlow 自有项目改造指南

这份指南面向第一次接手本仓库的前端开发者。项目仍保留 DeerFlow 的引擎与协议，产品页面和品牌由本仓库管理；账号、会话、文件的真正权限边界仍在 Gateway，不能只依赖前端隐藏入口。

## 先理解项目分层

```text
浏览器
  └─ frontend/ Next.js 产品界面
       ├─ src/product/       自有品牌、页面、产品文案、配置 DTO、功能展示开关
       ├─ src/app/           URL 路由和布局；只放必要的产品接入点
       ├─ src/core/          认证、API、会话、流式响应等引擎交互
       └─ src/components/    通用 UI 与工作台组合组件
          ↓ 同源 /api
backend/app/                 FastAPI Gateway、登录、权限与 API
backend/packages/harness/    DeerFlow Agent、沙箱、记忆、持久化
backend/packages/extension-api/
                             上游支持的自有扩展契约
product/backend-extension/   自有版本 Gateway API 与后续业务数据扩展
```

`frontend/src/core/threads` 和 `components/workspace/chats` 是复杂度最高的核心区，负责消息顺序、流式重连、停止任务、历史分页、产物和工具状态。修改产品风格时，从页面组合与 CSS 变量入手；只有需求确实涉及交互行为时才改这些核心逻辑。

## 常见前端任务

| 你要改什么           | 从这里开始                                                               | 注意事项                                                               |
| -------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 产品名称、简称、简介 | `frontend/src/product/brand.ts`                                          | 不改 `deerflow_*` 协议名和浏览器存储键                                 |
| 工作台/公开页品牌名  | `frontend/src/product/{document-title.tsx,public-brand.tsx,hooks.ts}`    | 登录/首页通过仅返回名称的公开接口更新；metadata 与失败状态保留源码回退 |
| 首页和工作台介绍文案 | `frontend/src/product/copy.ts`                                           | 中英文结构保持一致                                                     |
| 首页视觉             | `frontend/src/product/landing-page.tsx`                                  | `frontend/src/app/page.tsx` 仅选择 locale 并渲染页面                   |
| 登录后首页           | `frontend/src/product/workspace-home.tsx`                                | 通过现有 hooks 获取服务器数据                                          |
| 菜单功能显隐         | `frontend/src/product/features.ts`                                       | 这是 UI 开关，不授予或撤销 API 权限                                    |
| 登录 / 初始化外观    | `frontend/src/app/(auth)/login/`、`setup/`                               | 保留已有认证状态机、CSRF、Cookie 和登录回跳                            |
| 会话列表和聊天内容   | `frontend/src/core/threads/`、`frontend/src/components/workspace/chats/` | 先阅读相邻 `AGENTS.md` 和 hook 的数据契约                              |
| 全局颜色、边框与圆角 | `frontend/src/styles/globals.css`                                        | 通过 CSS 变量统一调整，不覆盖生成组件源码                              |
| 中文错误和按钮文字   | `frontend/src/core/i18n/locales/zh-CN.ts`                                | 新交互也要同步维护 `en-US.ts`                                          |

前端依赖安装后，在 `frontend/` 中使用 `pnpm dev` 启动页面、`pnpm check` 检查 ESLint 与 TypeScript、`pnpm test` 运行单元测试。根目录的 `make dev` 会一起启动 Gateway 和代理，适合验证真实登录、权限与流式会话；单跑前端时要按 `frontend/AGENTS.md` 配置后端地址。

## 数据和接口由谁负责

- 当前已接入项目新建、编辑、归档、恢复、删除，会话删除，上传文件删除，项目文档回收站操作，计划任务管理、自定义 Agent 创建/实际更新/删除、用户资料更新、个人访问令牌创建/撤销，以及密码变更、本地账号注册、首个管理员初始化、OIDC 首次自动开通和已有账号 OIDC 登录审计。令牌事件只记录令牌 ID 和固定动作码；认证事件只使用服务端账号 ID 与固定动作码；均不记录凭据、邮箱、OIDC subject 或请求正文，且只在认证/仓储操作成功后投递。其他事件由 Gateway 在操作完成后生成，身份与追踪 ID 取自主机上下文；项目说明、计划提示词、上传文件名、Agent 描述/SOUL/模型配置、`USER.md` 正文和请求正文不会写入审计，批量回收站清理失败时也会记录失败操作。审计存储沿用 Flow Desk 扩展的独立表。其余业务 API 的审计、全账号数据导出/删除编排仍未完成，不能把现有能力误认为完整的数据治理闭环。
- 管理审计 API 用额外一条数据库记录计算 `has_more`，前端按该字段判断是否展示下一页；部署环境仍运行旧版 Gateway 时，前端按本页条数兼容判断。不要只用“本页刚好满”作为新版接口的分页依据，否则记录总数恰好整页时会开放一个空白页。
- 记忆页面主动导出/导入、清空及事实增删改由 Gateway 写入稳定动作码；只记录事实 ID，不记录记忆正文。聊天运行时自动写入的记忆仍不在此 HTTP 审计范围内。
- 页面不能直连 PostgreSQL、文件卷、Agent 沙箱或对象存储。
- 上传接口的 5xx 响应不能把 Gateway `detail` 直接显示在浏览器中：`core/uploads/api.ts` 统一丢弃服务端错误正文并保留 HTTP 状态，聊天提交流程通过中英文 locale 显示安全提示；4xx 的文件限制等可操作反馈继续保留。改这条链路时同步维护 `locales/types.ts`、两份 locale 和上传 API 回归测试。
- LangGraph 流式请求回调和会话提交失败也只显示 `conversation.streamFailed` 双语提示，不把 SDK/Gateway 异常文本放入 toast；保留历史刷新和乐观消息清理。实际作为 Agent 回复写入会话历史的错误内容属于运行结果，不由这条请求错误提示规则改写。
- 认证复用 `core/auth`；普通 HTTP 请求复用 `core/api/fetcher`，它负责同源凭据与 CSRF 语义。
- 线程与 SSE 复用 `core/threads` 和现有 LangGraph client；不要为产品层另建一份消息存储。
- 删除会话时，Gateway 在 durable delete reservation 内依次清理本地工作区、checkpoints、单独存储的 `run_events` 消息/执行事件、运行历史（包括用量记录）和会话元数据；durable 清理失败会返回通用错误，并在删除元数据前停止，让用户重试。运行记录清理必须保留当前删除 reservation，并对 owner 冲突失败关闭。各存储并非一个原子事务，浏览器会话关闭仍是 best-effort，因此这项改进不等于完整账号擦除。
- 产品专属 API 应新增带版本的 `/api/product/v1/*` 契约，并在后端校验服务端身份、管理员权限和资源 owner。
- `/api/product/v1/settings` 的 GET 使用 `preferences:read`，PUT/DELETE 使用 `preferences:write`；扩展必须在访问独立设置表前检查 Gateway principal 权限，前端撤权后停止查询、清掉旧缓存并禁用保存。
- 产品扩展最低依赖 Extension API `0.2.18`。偏好、文件目录和数据任务请求需调用公开异步 `require_data_scope()`；后台 worker 还须通过 `ExtensionRuntimeDeps.owner_data_authorizer` 由 Gateway 重载活跃账号、刷新服务端 OIDC vault 会话，并在领取和分页/删除检查点重验当前 route grant 与 owner/self scope。403 终止任务，503 延迟重试；任何 IAM 凭据或授权快照都不得写入任务行。历史列表按 scope 隐藏已撤权任务，中央 IAM 无法判定时整体返回 503。
- 个人数据任务按范围复用 Gateway 的 route grants：会话导出同时要求 `threads:read + runs:read`；项目、Agent、记忆和计划任务分别要求对应读取权；组合账号包汇总所有子范围读取权；文件范围同时检查线程与项目权限。删除按对应 `*:delete` 权限控制，计划任务使用 `threads:delete`，文件删除同时检查 `threads:delete + projects:delete`。扩展在创建任务及读取详情、取消和下载制品时都重新检查当前权限；前端映射维护于 `frontend/src/product/data-job-permissions.ts`，但服务端仍是最终边界。
- `GET /api/product/v1/bootstrap` 已接入前端品牌和导航；产品扩展新增用户设置 GET/PUT/DELETE API，写入独立 `flowdesk_user_settings` 表并运行自己的 Alembic chain。设置按 Gateway principal 的用户 ID 隔离，每项 JSON 上限 64 KiB；偏好页保存的工作台显示密度会应用到布局。`fd_0002` 增加设置写入/删除的事务审计和仅管理员可读的分页查询；`fd_0003` 增加带版本冲突保护的在线品牌名与 UI 开关配置，`GET /api/product/v1/version` 提供非敏感产品/引擎版本标识。管理审计页会把稳定的服务端动作码显示为中英文业务文案，并按屏幕宽度切换表格和卡片；未知动作使用通用文案。首次进入管理页需在扩展私有配置中启用 `administration` 显示开关且当前用户角色为管理员；示例配置见扩展 README。Gateway 核心认证层提供 session-only 管理员账号列表及启停 API；停用会废止现有会话/PAT、暂停排队中的计划任务，且排队任务发起前会复核账号状态。成功的启停操作现在通过公开 `AdminActionObserver` 契约写入产品自有审计表，仅传递操作者/目标 ID、固定动作码和追踪信息；停用时 Gateway 还会请求中止该账号的活动 Agent 任务，并在管理响应中区分已停止、跨节点待处理和未确认停止；不能把请求中止等同于所有任务已终止。账号变更后的审计投递是 best-effort，扩展缺失或写入失败时会在 Gateway 诊断中记录，且不会回滚账号变更。扩展不得直读宿主用户表。个人偏好页提供偏好导出/删除、计划任务定义删除、自建 Agent 定义删除，以及 Gateway reader 支持的会话历史、项目元数据、计划任务和 Agent 部分导出；后几类导出均有明确的 `partial` 覆盖说明。删除还支持通过 Gateway capability 清除本人会话及 Gateway 管理的工作区、checkpoint、消息事件、运行记录和 thread metadata；活动或失败项会保留并显示部分结果，可重新提交重试。其他已实现范围包括偏好、计划任务定义、自建 Agent 定义、本人的会话历史和项目空间，以及通过当前记忆后端清空本人记忆。项目移除会解除会话与项目的关联并把活动资料放入回收站；项目元数据删除后不可恢复，会话正文保留，回收站仍需单独清理。记忆删除仅在 Gateway 确认后端覆写 `clear_memory` 时开放，并要求输入 `DELETE MY MEMORY`；清空开始后无法回滚。跨存储清除不保证原子回滚；项目资料、凭据和账号级全量擦除仍未覆盖。记忆清理只调用配置后端提供的 owner-scoped 清空操作，不表示全账号擦除。数据任务必须在 operator-controlled `plugins[].config.data_jobs.enabled` 中启用；以上能力都不是账号全量导出或删除。业务 API 全面审计、宿主数据全账号导出/删除编排及更广泛的产品管理仍未实现，不能把现有能力误认为完整的数据管理闭环。
- DeerFlow 的旧资源和表由上游服务管理。产品私有设置、审计和数据任务应由独立扩展与迁移链管理，不能把产品表混入 Harness 的 ORM Base。
- Gateway 的扩展运行时提供可选 `owner_data_reader` 公共能力，按显式 owner ID 分页读取用户自己的线程摘要、Gateway 可见历史、项目白名单元数据和计划任务定义；宿主会再次检查资源 owner、复用隐藏运行过滤，并且不返回任意线程 metadata。Flow Desk worker 使用它执行会话、项目和计划任务定义的部分导出，不读写 checkpoint。计划任务投影只含提示词、助手、频率、时区、状态及时间戳，不含执行历史或运行时状态。产品扩展 `fd_0004`/`fd_0005`/`fd_0006` 已接入 owner 隔离、幂等、每人一个活动任务、每小时最多 10 个新任务、过期租约回收、进度栅栏、重试与取消 API/worker；API 只有在 operator 的 `plugins[].config.data_jobs.enabled: true` 显式启用后才开放。偏好导出/删除仍只处理 `flowdesk_user_settings`；后台导出最多 10 MiB、24 小时失效，并在任务结果和包内始终标记 `partial`，注明非快照分页和排除范围。它尚不是完整账号导出/擦除，账号页的现有导出仍是浏览器前台流程，`data_privacy` UI 开关保持关闭。
- 开发环境可以使用 SQLite；生产持久化必须盘点数据库、事件、Agent 定义、文件、记忆和加密材料。只配置 PostgreSQL 或只备份 SQL 都不够。
- `product/deploy/` 提供 PostgreSQL Compose 覆盖与配置片段，便于把账号、会话、checkpoint、run events、Agent 定义持久化在自有数据库。上传文件、工作区、记忆和加密材料仍要分别纳入备份；配置切换不会自动迁移旧 SQLite 数据。
- 腾讯云轻量应用服务器的容量、端口、HTTPS、首次管理员初始化和上线步骤见[服务器部署方案](plans/服务器部署方案.md)；该方案尚未在目标实例执行。
- 发布前检查、一致性备份记录、隔离环境恢复演练及升级回退边界见 [`product/deploy/OPERATIONS.md`](../product/deploy/OPERATIONS.md)。其中尚未在目标部署演练的步骤必须先经隔离验证，不能当作已验收的恢复方案。
- `files` 开关对应自有文件中心。扩展迁移 `fd_0007` 在产品自有数据库保存按当前用户隔离的文件元数据快照；首次访问、快照超过 5 分钟或请求显式刷新时，`GET /api/product/v1/files` 最多调用一次 Gateway `OwnerDataReader.list_files` 重建不超过 10,000 条的有界目录。数据库只存 Gateway 返回的 owner-scoped 元数据，不保存正文、宿主路径或授权凭据；每个用户只保留当前快照，刷新以事务切换并删除旧快照。手动刷新受每用户 30 秒冷却和跨实例刷新租约限制，延后时响应 `catalog_refresh_deferred`；扫描失败时保留上次快照并通过 `catalog_stale` 和覆盖提示告知页面。文件名、会话名和项目名搜索以及 50 条一页分页在产品目录上完成，避免翻页时重复遍历磁盘。目录覆盖当前用户线程上传/输出、会话工作区和项目资料架原件；Gateway 最多扫描 5,000 个会话、5,000 个项目、每个会话工作区 200 个目录、单次总计 20,000 个工作区目录。生成目录、符号链接和 Windows 联接点会跳过；达到上限或数据源读取失败时提示结果不完整。工作区文件在文件中心只读，打开或下载继续调用 Gateway 原有 owner-scoped 文件路由，删除仍只对支持删除的来源开放。后台文件导出现在包含有界工作区文件，但会跳过敏感名称路径且不扫描正文密钥，仍排除派生预览和回收站。启用前需要确认 Gateway 已授予 `threads:read`、`projects:read` 且文件 API 鉴权配置正确。
- Gateway 删除成功后，产品 `DELETE /api/product/v1/files/catalog-entry` 只移除当前用户快照中的元数据行并标记需要重建，不执行或替代文件删除。
- 账号设置的“导出我的数据”目前提供前台一次性 JSON 包，尽力覆盖当前登录账号通过 Gateway API 可读的会话、项目、Agent、定时任务、记忆、偏好和附件；附件还会通过一次有界的 owner-scoped 文件目录请求补入合格的会话工作区文件，并使用 Gateway 再次校验 owner 的下载 URL。敏感名称与非跨平台相对路径会被跳过，目录截断或读取失败会记入包内；用户可取消导出，离开设置页时会停止，附件最多 100 MiB；不会读取部署凭据存储或可恢复的 LangGraph checkpoint，但普通用户文件正文不扫描密钥，分享前需检查。也没有后台重试、账号删除任务、完整索引或备份恢复，所以 `data_privacy` 继续关闭，不能把它描述成完整迁移备份。
- 文件中心还使用 Gateway 的 owner-scoped `/api/threads/{id}/uploads/outputs` 只读接口发现未归属项目的 Agent 输出；接口最多返回 200 项并报告截断，输出文件当前没有删除 API，页面不会显示删除操作。
- 后台数据任务还支持项目元数据部分导出：只包含当前用户项目的名称、说明、展示配置、状态和时间戳；项目文档正文、文件、checkpoint、跨对象事务快照均不包含。每页由 Gateway reader 限定 owner，包限制 5,000 个项目/10 MiB，并在任务与 JSON 包中标注 `partial`。项目空间也支持单范围删除：Gateway 按显式 owner 删除项目元数据、解除会话关联，并把活动项目资料移入回收站；项目元数据删除后不可恢复，会话正文保留，回收站仍需单独清理。账号级 `data_privacy` 保持关闭。
- 个人数据页提供组合数据 ZIP 导出：合并偏好、会话、项目、计划任务、自建 Agent、当前记忆 backend 与受限文件七种已有 owner-scoped 导出，包内 `manifest.json` 列出每类是否包含、失败或受大小上限遗漏。会话数据含 Gateway 可见消息及经过 owner 校验的运行摘要/token 用量；计划任务定义包不含 occurrence/run 历史。每种数据仍沿用单项导出的限制，组合包上限 64 MiB 并始终标记 `partial`；凭据、部署配置、LangGraph checkpoint 和运行续接状态不包含在内，故不是完整账号备份。组合导出只扩展读能力，不提供账号级删除，也不启用 `data_privacy`。
- 设置页的文件删除任务要求 `DELETE MY FILES`，只永久删除本人线程上传，并将项目资料放入可恢复回收站；生成产物和工作区文件保留且会让结果标记为部分完成。实现经过 DeerFlow `OwnerDataDeleter` 可选契约和 Gateway owner 边界，不直接访问宿主表或接受文件系统路径；升级时需保持旧宿主缺少 capability 时在 API 层失败关闭。
- 后台数据任务还支持计划任务定义部分导出：只包含当前用户的计划任务定义、提示词、助手、频率、时区、状态和时间戳，不包含执行历史、运行 ID、运行时错误、租约或凭据。导出受 5,000 条和 10 MiB 上限约束，在任务与 JSON 包中标注 `partial`；它不是计划任务迁移的事务快照，删除 API 也不允许删除计划任务。
- 后台数据任务还支持文件部分导出：Gateway `OwnerDataReader.read_files` 仅返回当前 owner 的平铺线程上传/输出、每个会话最多扫描 200 个目录且全任务合计最多扫描 20,000 个目录的工作区文件，以及项目资料架 active 原件，并在每次读取时重验线程或文档归属。宿主拒绝符号链接和 Windows 联接点、不返回路径，跳过生成目录与敏感名称路径；正文不做密钥扫描，页面提示分享前复核；仍排除转换预览、回收站和部署文件；每包最多 5,000 个文件、7 MiB 原始内容、10 MiB JSON，超限或读取失败会标记为部分结果。该能力不是持久化文件索引或完整备份，删除任务也不允许删除这些文件。

## 怎样跟进上游升级

在 Codex 对话中发送 `--升级`，即可执行仓库内的 [DeerFlow 上游升级 Skill](skills/deerflow-upgrade/SKILL.md)。它会先检查官方最新稳定 Release、本地版本、Git 来源关系和 `docs/上游补丁台账.md` 的产品补丁，再决定能否安全升级；没有更新时会留下带日期的检查记录。这个触发词不是终端命令。

当前 Git 历史只有一个 `first commit`，`origin` 指向自有仓库，也没有可用于普通 merge 的上游祖先提交。因此当前状态无法证明本地代码与哪一个 DeerFlow 上游 commit 一一对应。不要直接把新上游文件覆盖进来，也不要把 `origin` 改回上游地址。

已有隔离的官方源码克隆时，可在仓库根目录用 `python scripts/compare_upstream_trees.py --local-repo . --local-ref <本地来源提交> --upstream-repo <隔离官方克隆路径> --upstream-ref <官方 tag>` 读取两份已提交 tree 的路径、模式和对象 ID 差异。脚本只向标准输出生成清单；仍需逐项判断来源和产品补丁，当前工作区的未提交改动也要单独审查。

建立可验证升级基线后，每次升级按以下顺序操作：

1. 确认自有 `origin`、许可证和当前部署备份；记录现有版本及配置迁移号。
2. 选定官方上游 commit 和许可证兼容的同步方式，建立可以重复应用的来源/补丁台账。
3. 在隔离候选分支按来源清单移植或重做更改，并归类上游核心、产品接入、品牌文案和产品后端扩展；只有确认共同祖先后才使用普通合并。
4. 检查 API、身份投影、消息/SSE、用户数据路径、数据库迁移和配置 schema 的兼容性。
5. 运行前后端检查与必要的真实数据库联调；在生产数据副本上恢复备份并升级，再回退演练。
6. 记录升级前后 commit、补丁处理、迁移结果、测试结果和回退点，然后再部署。

将产品代码放在 `frontend/src/product/` 和独立扩展目录只能减少冲突，不能自动保证兼容；每次升级仍须验证公开 API 与运行契约。

## 已落地的自有前端边界

- `frontend/src/product/` 维护品牌、双语文案、功能入口和自有首页/总览。
- `frontend/src/app/` 保留 Next.js 既有路由，避免复制认证和工作台页面树。
- 未实现的产品 API 及数据管理功能不暴露入口。
- `deerflow_*` 元数据、localStorage key、LangGraph 路由及 Python 包名继续作为引擎兼容标识。
- MIT 许可要求随分发保留上游版权和许可证声明；产品 About 页面把自有身份与上游来源分开展示。
- `/docs` 和 `/blog` 共用 Flow Desk 导航，GitHub 链接明确指向 DeerFlow 开源引擎来源；本地页面不再显示上游仓库的编辑入口。文档内容中的 DeerFlow 技术名称和兼容说明仍按引擎事实保留。
