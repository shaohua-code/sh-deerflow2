# DeerFlow 前端项目结构说明

> 面向前端开发者的代码导航。此文对应当前仓库结构；目录可能随上游升级变化，改动前请同时检查 `frontend/AGENTS.md` 和 `frontend/src/AGENTS.md`。

## 1. 技术栈与入口

- Next.js App Router、React、TypeScript、Tailwind CSS。
- `frontend/src/app/` 是路由和页面入口；`frontend/src/core/` 是可复用业务逻辑；`frontend/src/product/` 是本项目自有产品边界。
- 默认开发入口：仓库根目录执行 `make dev`；单独调前端可进入 `frontend/` 执行 `pnpm dev`。常用质量检查为 `pnpm check`、`pnpm test`。
- 标准本地部署由 Nginx 暴露 `http://localhost:2026`。前端通常走同源 `/api`，不要为了产品定制绕过现有 CSRF、身份和 SSE 处理。

## 2. 目录速览

```text
frontend/
├── public/                    # 静态文件、图标、图片
├── src/
│   ├── app/                   # Next.js App Router：路由布局、页面、route handlers
│   ├── components/            # 展示组件；workspace、landing、docs 等业务组件
│   │   ├── ui/                # Shadcn 生成的基础组件
│   │   ├── ai-elements/       # AI SDK 生成/适配组件
│   │   └── workspace/         # 工作台、聊天及管理界面组件
│   ├── content/               # 博客、产品文档等 MDX 内容
│   ├── core/                  # API、会话、认证、权限、文件等领域逻辑
│   ├── hooks/                 # 跨页面复用的 React hooks
│   ├── lib/                   # 通用小工具（例如 cn）
│   ├── product/               # 本产品的品牌、文案、导航显隐和页面组合
│   ├── styles/                # 全局 CSS、Tailwind 主题、设计 token
│   └── typings/               # 全局 TypeScript 声明
├── tests/
│   ├── unit/                  # 与 src 结构对应的单元/DOM 测试
│   └── e2e/                   # Playwright 用户流程测试
├── env.js                     # 环境变量校验
├── mdx-components.ts          # MDX 组件映射
└── package.json               # 脚本及依赖
```

## 3. 路由与页面在哪里

`src/app/` 的目录名直接映射 URL。当前主要入口包括：

| 路由/目录                       | 用途                          | 改页面时先看                                 |
| ------------------------------- | ----------------------------- | -------------------------------------------- |
| `app/page.tsx`                  | 产品公开首页                  | `product/landing-page.tsx` 与首页组件        |
| `app/workspace/`                | 登录后工作台、聊天及管理页    | 对应 page/layout 与 `components/workspace/`  |
| `app/(auth)/`                   | 登录、初始化和认证回调        | 认证页面及 `core/auth/`                      |
| `app/showcase/[thread_id]/`     | 公开展示线程                  | showcase 页面与权限白名单                    |
| `app/artifacts/view/`           | 独立产物查看窗口              | `core/artifacts/` 和 viewer 组件             |
| `app/api/`                      | Next.js 服务端 route handlers | 判断是否应属于 Gateway；避免重复实现后端业务 |
| `app/[lang]/docs/`、`app/blog/` | 本地化文档和博客              | `content/`、MDX 映射                         |

本产品自有首页和工作台总览组合放在 `src/product/`，路由文件尽量保持薄，只负责取参数、加载数据和挂载页面组件。复杂聊天页面优先复用 DeerFlow 原有组件与 hooks，避免复制一套 SSE/取消/重连实现。

## 4. `core/` 领域逻辑

`core/` 是前端最重要的业务层。页面组件负责交互和布局，领域逻辑集中在这里，方便测试并减少上游升级时需要重做的范围。

| 领域目录                                       | 责任                                               | 常见改动                                  |
| ---------------------------------------------- | -------------------------------------------------- | ----------------------------------------- |
| `core/api/`                                    | Gateway/LangGraph 客户端、请求封装、CSRF、静态响应 | 新 API 客户端或错误处理                   |
| `core/threads/`                                | 会话创建、消息发送、流式事件、恢复、取消           | 聊天生命周期；改动风险高，先读线程 AGENTS |
| `core/auth/`                                   | 登录态、会话、权限和认证客户端                     | 登录接入；服务端权限仍由后端强制执行      |
| `core/artifacts/`                              | 文件/产物查询、呈现及 viewer 模型                  | 文件中心、产物预览                        |
| `core/agents/`、`core/subagents/`              | Agent 配置与子任务目录                             | Agent 管理、执行能力展示                  |
| `core/skills/`、`core/mcp/`、`core/tools/`     | Skills、MCP 和工具配置                             | 能力中心与集成设置                        |
| `core/projects/`、`core/tasks/`、`core/todos/` | 项目、调度任务和待办                               | 工作台业务页                              |
| `core/settings/`、`core/models/`               | 设置与模型信息                                     | 产品设置页及模型配置                      |
| `core/memory/`、`core/messages/`               | 记忆与消息辅助能力                                 | 记忆页面及消息显示                        |
| `core/i18n/`                                   | 英文/中文消息资源与 locale                         | 新 UI 文案必须同步双语资源                |

## 5. 请求与数据流

```text
App Router 页面
  └─ 展示组件 / React hook
       └─ core/<domain> 客户端和状态
            ├─ LangGraph SDK → /api/langgraph/* → Gateway 运行时 / SSE
            └─ Gateway REST → /api/* → Gateway router → service / persistence
```

聊天属于有状态、长连接流程：页面 hook 创建或选择 thread，发送消息后消费 SSE；服务端事件更新消息、工具/子任务状态和产物；断线恢复、取消和历史读取要沿用 `core/threads/` 的既有实现。普通设置页可使用 REST/TanStack Query 模式。自有 bootstrap API 的类型和调用适配位于 `src/product/api.ts`；它不是授权依据，敏感操作仍须由 Gateway 验证身份和权限。

## 6. 自有产品改造边界

当前推荐边界：

- 品牌名、文案、产品展示能力：`src/product/brand.ts`、`copy.ts`、`features.ts`。
- 自有首页、工作台入口、品牌标识：`src/product/` 下的页面组合和 `brand-mark.tsx`。
- 自有 bootstrap / 用户偏好 / 审计请求：`src/product/api.ts`、`hooks.ts`、`settings-hooks.ts`；复用身份感知 fetcher、CSRF 和 TanStack Query 用户分区缓存。`components/workspace/settings/product-preferences-page.tsx` 和 `product-admin-page.tsx` 是首个接入产品 API 的偏好与管理员审计页面；管理员入口同时要求服务端功能开关和前端角色显示条件，Gateway 仍独立授权。
- 文件中心和账户导出：`src/product/file-center-page.tsx`、`api.ts`、`data-export.ts`。文件中心通过 `/api/product/v1/files` 读取登录用户的上传、输出、会话工作区和项目文档元数据；首次加载时读取一次有界目录，之后在浏览器内按文件分页并搜索文件名、对话名和项目名。工作区文件只读，扫描有上限并明确报告不完整结果，文件正文仍由 Gateway 既有授权 URL 提供。该目录是按请求构建的临时视图，不含正文搜索或持久索引；后台文件导出已包含受限工作区文件，仍排除派生预览、回收站和凭据名称路径。账号 JSON 导出是前台多请求快照；后台会话数据任务还导出可见消息和安全运行摘要，但不包含凭据、可恢复 checkpoint 或运行续接状态。
- 新增自有产品组件：放在 `product/`；通用 DeerFlow 组件才放 `components/`。
- 产品主题：复用 `src/styles/` 的 CSS 变量，不在每个页面硬编码颜色。
- 导航显隐只控制展示，不代替后端授权。
- 对上游核心流程的修改必须记录到 `docs/上游补丁台账.md`，说明原因、文件、测试和升级时的复核方式。

不要直接改 `components/ui/`、`components/ai-elements/` 里的生成组件；如需调整外观，在产品层封装、传入样式或调整设计 token。原生 DeerFlow 聊天域变化较频繁，品牌页面与复杂会话逻辑保持分离，可降低合并冲突。

## 7. 新增页面的推荐步骤

1. 确认路由归属：产品专属页面进 `app/` 路由并由 `product/` 组合；通用会话功能沿用 `workspace` 与 `core/`。
2. 先查 `core/` 是否已有数据客户端、权限钩子和类型，尽量复用。
3. 定义 loading、空数据、错误、无权限和窄屏状态，不只实现成功态。
4. UI 文案同时补 `core/i18n/` 对应中英文资源。
5. 逻辑测试放 `tests/unit/` 镜像路径；涉及 React DOM 才用 `.dom.test.tsx`；用户主路径补 E2E。
6. 运行 `pnpm check` 和受影响测试；必要时从根目录做登录聊天联调。
7. 更新产品文档及补丁台账，说明新增的上游接缝。

更多实现约束见 [`frontend/AGENTS.md`](../frontend/AGENTS.md)、[`frontend/src/AGENTS.md`](../frontend/src/AGENTS.md) 和[产品化指南](自有项目改造指南.md)。

# DeerFlow 后端项目结构说明

> 面向前端开发者与产品改造者的后端导航。仓库包含 Gateway 应用、Agent Harness 和公开扩展 API；深入修改模块前先读该目录的 `AGENTS.md`。

## 1. 先认识运行方式

后端主要是两个层次：

- **Gateway（`backend/app/`）**：FastAPI 应用，承接 HTTP、认证授权、运行管理、后台服务和 IM 通道。
- **Harness（`backend/packages/harness/`）**：可复用的 DeerFlow Agent 框架，负责组装模型、提示词、中间件、工具、子 Agent、沙箱和持久化。
- **公开扩展合同（`backend/packages/extension-api/`）**：第三方产品扩展可依赖的稳定接口，应优先通过它扩展，减少直接依赖 Harness 内部细节。
- **本项目产品扩展（`product/backend-extension/`）**：自有 HTTP API 与业务功能，独立于上游 `app/`、Harness 和各自迁移链。

本地 `make dev`、Docker 和生产均由 Gateway 内嵌启动 Agent Runtime。Nginx 是对外入口：浏览器访问 `/api/langgraph/*` 时，Nginx 转发并改写到 Gateway 原生 `/api/*` 路由。端口说明：Nginx 2026、Gateway 8001、前端 3000、可选 Provisioner 8002。

## 2. 目录结构

```text
backend/
├── app/                              # FastAPI Gateway 应用层
│   ├── gateway/                      # API、认证授权、服务装配、路由
│   ├── channels/                     # 飞书、Slack、Telegram 等 IM 通道
│   ├── scheduler/                    # 后台定时任务调度服务
│   └── mcp_tasks/                    # 耐久 MCP 任务服务
├── packages/
│   ├── extension-api/                # deerflow_extension_api：扩展公开合同
│   └── harness/                      # deerflow-harness：Agent 引擎
│       └── deerflow/
│           ├── agents/                # 主 Agent、状态、记忆、任务连续性
│           ├── runtime/               # Agent 执行、RunManager、StreamBridge
│           ├── middleware/             # 模型上下文和工具链中间件
│           ├── tools/                 # 内置工具、MCP、社区工具
│           ├── subagents/              # 子 Agent 注册与后台执行
│           ├── sandbox/                # 代码执行和文件系统隔离
│           ├── persistence/             # 用户、任务、记忆、迁移及数据库适配
│           ├── config/                  # 配置模型、读取和路径
│           ├── extensions/              # Python 扩展加载和生命周期
│           ├── models/                  # LLM 工厂与模型适配
│           ├── skills/                  # Skill 发现和加载
│           └── mcp/                     # MCP 客户端、工具和配置适配
├── tests/                              # Gateway/Harness 后端测试
├── scripts/                            # 迁移、运维及可复现基准工具
├── docs/                               # 后端配置和模块文档
└── Makefile                            # 后端开发、测试、lint 命令

product/
└── backend-extension/                  # 本产品扩展包、路由、服务和自有测试
    └── flow_desk_product_extension/
        └── migrations/                  # 自有 Alembic chain；当前含用户设置首个 revision
```

具体包的目录会继续拆分；以上是职责导航。可用 `rg --files backend/app backend/packages/harness/deerflow` 找当前文件，不要仅凭旧文件名写代码。

## 3. Gateway 请求路径

```text
浏览器
  → Nginx /api/*
  → FastAPI Gateway 中间件（认证、CSRF、权限、追踪）
  → router
  → service / extension service
  → Harness、领域仓储或第三方系统
  → SQL 数据库 / 文件存储 / 配置
```

`backend/app/gateway/` 中的 `app.py` 与服务装配负责创建应用和注册路由；各 router 接收并验证请求，再调用服务。产品扩展通过公开 extension API 注册 Gateway service/router，避免在上游核心里塞入品牌或专属业务逻辑。身份必须从 Gateway 可信认证上下文解析；不可相信前端传来的 `user_id` 或 header 自报身份。

Agent 执行是特殊的长流程：Gateway 接受 LangGraph 兼容请求，RunManager 建立运行生命周期，由 Harness 的 `run_agent()` 执行，StreamBridge 把事件转为 SSE；运行状态、checkpoint、取消、重连和调度都具有持久化/并发约束。前端需要扩展聊天行为时先确认公开 API 是否足够，不要新增一条并行执行引擎。

## 4. 模块责任

| 模块 | 负责什么 | 改造时注意 |
| --- | --- | --- |
| `app/gateway/` | HTTP 路由、服务容器、身份认证授权、健康检查和 Agent Gateway | 所有自有 API 也必须经过服务端身份与权限检查 |
| `app/channels/` | IM webhook、消息映射、会话关联和各渠道策略 | 保持每渠道身份映射与去重语义 |
| `app/scheduler/` | 定时运行派发、队列、租约和恢复 | 不要绕开正常 Gateway run 生命周期 |
| `app/mcp_tasks/` | 长耗时 MCP 作业的提交、查询、取消、重试/通知 | 数据库为任务权威状态，须保留租约和取消边界 |
| `packages/extension-api/` | 扩展身份投影、贡献接口与运行桥接 | 这是产品扩展优先依赖的 API 合同 |
| `harness/deerflow/agents/` | Lead Agent、ThreadState、记忆与任务上下文 | 系统提示词和状态 schema 会影响运行行为 |
| `harness/deerflow/runtime/` | Agent 执行生命周期及 SSE 桥接 | 高风险核心，严格回归取消、恢复、子任务和流事件 |
| `harness/deerflow/persistence/` | 数据仓储、模型与上游迁移 | 产品业务表使用独立表前缀和独立迁移链 |
| `harness/deerflow/sandbox/` | 命令、文件和沙箱 provider | 用户数据路径、挂载及权限变化要做安全审查 |
| `harness/deerflow/extensions/` | 扩展发现、加载、排序和隔离 | 扩展代码有 Gateway 权限，只安装可信来源 |
| `product/backend-extension/` | 自有 API/业务接入点 | 不直接侵入 `backend/app` 或 Harness；写清合同和兼容测试 |

## 5. 数据及配置边界

不要把“数据”当成一张数据库表。至少区分：

- **关系数据库**：用户和授权、任务/调度、配置型数据、运行事件或 checkpoint（按配置启用）。生产建议 PostgreSQL；本地默认 SQLite 便于启动。升级数据库前先读持久化迁移指南。
- **文件与工作区**：上传文件、Agent 产物、项目文件以及运行沙箱内容，实际路径由配置及用户目录解析决定。仅备份数据库会漏掉文件。
- **记忆与状态**：记忆服务、ThreadState 投影、checkpoint 的存储后端可能不同；不能假设它们同库。
- **配置与密钥**：根目录 `config.yaml` 控制运行时，`extensions_config.json` 存 MCP/skills 设置；均可能包含敏感值且被 gitignore。生产密钥应走部署密钥管理。
- **产品业务数据**：新增数据归 `product/` 产品扩展负责；定义保留期、所有权、导出和删除流程，并与用户资源 ID 做服务端关联。

`config.yaml` 和 `extensions_config.json` 源自 example 模板。首次启动用 `make config` 生成，再运行 `make install`、`make dev`。修改模板或部署文档时同步解释数据目录、密钥和备份范围。

## 6. 自有扩展和上游兼容

新增产品 API 放入 `product/backend-extension/`，依赖 `deerflow-extension-api`，由受信任的 `plugins:` 配置安装/启用。API 路径采用 `/api/product/v1/`，请求 DTO 显式版本化。用户偏好已通过自有 `flowdesk_` 前缀表和独立 Alembic version table 持久化；PostgreSQL 位于 `product` schema。将插件记录的 `table_prefix` 设为 `flowdesk_`，让上游 autogenerate 忽略产品表。后续业务表沿用自有迁移链，避免与上游 Alembic 修订交织。扩展启用和代码导入是运维级操作，不能由普通用户 API 动态任意加载。

文件 API 的文件夹身份必须由 Gateway 当前 principal 派生。上传列表只包含 uploads 输入；`GET /api/threads/{id}/uploads/outputs` 是新增的只读输出列表，复用 `threads:read` owner-check，最多返回 200 个文件并以 `truncated` 明确提示被截断。该列表不创建索引，也不授予输出文件删除权限。

产品数据 worker 通过公开 `OwnerDataReader` 按显式 owner 读取会话摘要、可见消息、计划定义及运行摘要。运行摘要只包含 run/Agent 标识、状态、时间和 token 计数；Gateway 先验证线程归属，再以相同 owner 查询 RunStore，并按 `(created_at, run_id)` 倒序分页。原始 kwargs、错误正文、metadata、stop reason、checkpoint 和 worker lease 不得越过 Gateway 边界。新增 reader 方法时，需同步升级 `deerflow-extension-api`、Harness 精确 pin、产品扩展最低版本与扩展声明，并验证旧 reader 缺少可选能力时的部分结果提示。

升级上游时先确定真实基线，然后依序运行 Harness/Gateway 测试、产品扩展单测、前端 API contract 和端到端登录/运行/文件流程。记录冲突文件及必要重放步骤到 [`docs/上游补丁台账.md`](上游补丁台账.md)。Git 来源和可合并基线现况见[整体 PRD](plans/产品化需求与实施记录.md)；不可把“目录分开”误当成“无需做升级测试”。

## 7. 修改和验证流程

1. 找对应模块的 `AGENTS.md`，确认数据流、错误处理、线程/异步边界和迁移规则。
2. 优先复用 Gateway 服务、Harness hook 或 extension API。若无稳定合同，再把核心改动控制为小补丁并记录。
3. 更新 Pydantic DTO、权限、API 文档及前端类型；错误响应保持稳定、不要泄露内部异常或密钥。
4. 后端按测试类型运行 `cd backend && make test`；受影响的文件可用 `python -m pytest tests/path/to/test.py -q`。运行 lint/format：`cd backend && make lint && make format`（提交前确认工作区 diff）。
5. 涉及数据库时增加迁移并测试升级和回滚/恢复策略；涉及并发/租约时测多 worker 与进程重启场景。
6. 根目录运行整体服务验证，确认 Nginx 转发、浏览器登录和真实 SSE 主链路。
